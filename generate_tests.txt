# Pruebas Unitarias y de Integración Detalladas para la Migración (Python + Supabase)

A continuación, se detalla una lista estructurada para pruebas manuales y automatizadas enfocadas en el nuevo stack tecnológico. Cada escenario incluye la precondición, los pasos exactos a seguir, y el resultado esperado según la lógica de negocio migrada.

---

## 1. Pruebas de Semáforo (Cálculo de SLAs) para Clasificación de Tareas
**Objetivo:** Validar la lógica del backend (Python) para las alertas visuales y el cálculo de estado de los SLAs en la base de datos (Supabase).

### Escenario 1.1: Clasificación A (Límite 3 días)
- **Precondición:** Se tiene una tabla/vista de tareas en el frontend conectada a la API.
- **Pasos:**
  1. Insertar una tarea mediante la API y asignar "A" en el campo `clasificacion`.
  2. Establecer la fecha de inicio (`fecha`) como el día de hoy.
  3. Modificar la fecha de inicio (via API o interfaz) para simular **1 día** de antigüedad (hoy - 1 día).
  4. Modificar la fecha para simular **2 días** de antigüedad (hoy - 2).
  5. Modificar la fecha para simular **4 días** de antigüedad (hoy - 4).
- **Resultado Esperado:**
  - Tras los pasos 2 y 3, el endpoint debe retornar un estado de SLA que el frontend renderice como **Verde** (A tiempo).
  - Tras el paso 4, el estado debe retornar un flag de alerta temprana, renderizándose **Amarillo** (Por vencer).
  - Tras el paso 5, el estado debe marcar SLA incumplido, renderizándose **Rojo** (Vencido).

### Escenario 1.2: Clasificación AA (Límite 14 días)
- **Precondición:** Igual que arriba.
- **Pasos:**
  1. Asignar "AA" en `clasificacion`.
  2. Establecer una fecha con **11 días** de antigüedad.
  3. Establecer una fecha con **13 días** de antigüedad.
  4. Establecer una fecha con **16 días** de antigüedad.
- **Resultado Esperado:**
  - Paso 2: **Verde**.
  - Paso 3: **Amarillo** (avisa días antes del límite 14).
  - Paso 4: **Rojo**.

### Escenario 1.3: Clasificación AAA (Límite 30 días)
- **Precondición:** Igual que arriba.
- **Pasos:**
  1. Asignar "AAA" en `clasificacion`.
  2. Modificar la fecha a **24 días** de antigüedad.
  3. Modificar la fecha a **27 días** de antigüedad.
  4. Modificar la fecha a **32 días** de antigüedad.
- **Resultado Esperado:**
  - Paso 2: **Verde**.
  - Paso 3: **Amarillo**.
  - Paso 4: **Rojo**.

## 2. Pruebas de Permisos de Ruteo y Vistas de Ventas (La Ley de Antonia)
**Objetivo:** Validar que los endpoints (Python) y los roles de seguridad (Row Level Security - RLS en Supabase) aíslan las ventas exclusivas de Antonia y protegen los dashboards.

### Escenario 2.1: ANTONIA_VENTAS manda tarea a un vendedor
- **Precondición:** Iniciar sesión con el usuario autenticado como `ANTONIA_VENTAS`.
- **Pasos:**
  1. Seleccionar a un vendedor (ej. `EDUARDO MANZANARES`) en el campo responsable, especificando el contexto de `VENTAS`.
  2. Enviar el POST a la API para crear la tarea/cotización.
- **Resultado Esperado:** La tarea se guarda íntegra en Supabase y aparece exitosamente en la vista o dashboard de ventas de `EDUARDO MANZANARES`. El backend autoriza y respeta este ruteo por el rol de Antonia.

### Escenario 2.2: Otro usuario intenta mandar tarea al contexto de ventas
- **Precondición:** Iniciar sesión con un rol diferente (ej. un administrador o empleado operativo como `LUIS_CARLOS`).
- **Pasos:**
  1. Modificar el payload para intentar asignar la tarea al contexto de ventas de otro empleado.
  2. Ejecutar el POST.
- **Resultado Esperado:** El backend interceptará la petición, ignorará/limpiará el contexto de ventas, y asignará la tarea obligatoriamente a la tabla o vista de **Operaciones/Tracker general** del empleado, impidiendo que contamine el pipeline de ventas.

### Escenario 2.3: Alguien intenta enviar tareas generales al core de Ventas
- **Precondición:** Iniciar sesión como `EDUARDO MANZANARES` (operativo).
- **Pasos:**
  1. Seleccionar como responsable a `ANTONIA_VENTAS`.
  2. Enviar la tarea.
- **Resultado Esperado:** El backend de Python sabe que "Nadie manda tareas al core de cotizaciones". Muta automáticamente el `user_id` de destino hacia el perfil personal de `ANTONIA PINEDA LOPEZ` (su tracker operativo). El folio auto-generado nacerá con el prefijo personal `AP-`, descartando el prefijo maestro de ventas `AV-`.

## 4. Pruebas de Concurrencia, Gatekeeper y Auto-Archivado
**Objetivo:** Validar las transacciones ACID de Supabase (PostgreSQL) y las reglas de negocio de cierre.

### Escenario 4.1: Protección Anti-Spam (Race Conditions)
- **Precondición:** Preparar un script para enviar peticiones concurrentes a la API.
- **Pasos:**
  1. Enviar 5 peticiones POST idénticas de "Nueva Tarea" (con el mismo `idempotency_key` o `temp_id`) simultáneamente.
- **Resultado Esperado:**
  1. La base de datos (o la capa de caché/Redis en Python) utilizará la clave de idempotencia o bloqueos transaccionales (Locks) para aceptar solo la primera petición, respondiendo con éxito (200/201).
  2. Las 4 peticiones restantes serán descartadas (o retornarán el mismo recurso ya creado), garantizando que solo exista 1 registro en Supabase.

### Escenario 4.2: Upsert / Fallback Orgánico
- **Precondición:** Se tiene un registro en la base de datos sin un FOLIO explícito (o un sistema externo envía datos parciales).
- **Pasos:**
  1. Enviar un payload de actualización (PUT/PATCH) enviando: Concepto exacto, Cliente exacto y Fecha exacta, sin incluir un ID primario.
- **Resultado Esperado:** El backend realizará una consulta de validación cruzada. Al detectar coincidencia exacta de esos tres parámetros, ejecutará un UPDATE sobre la fila existente en Supabase en lugar de ejecutar un INSERT, evitando la duplicidad.

### Escenario 4.3: Auto-Archivado (Estado de Completado)
- **Precondición:** Tarea en estado `ASIGNADA`, Avance: 0.
- **Pasos:**
  1. Enviar PATCH con el avance a `100` (entero).
  2. Enviar PATCH con el avance a `"100%"` (string).
  3. Enviar PATCH con el estatus a `DONE` o `HECHO`.
- **Resultado Esperado:** En los tres casos, el backend actualiza el estado de la tarea a `completado` o activa un flag `is_archived = true` en Supabase. Las vistas (Views) operativas filtrarán automáticamente esta fila, mostrándola únicamente en los endpoints de "Historial" o "Tareas Realizadas".

## 5. Pruebas de Distribución Lateral (El Papa Caliente) y Sincronización Bidireccional
**Objetivo:** Validar el motor de workflows basado en estados (BPM) de Python.

### Escenario 5.1: Delegación "Papa Caliente"
- **Precondición:** `ANTONIA_VENTAS` tiene una cotización maestra registrada `AV-5050`.
- **Pasos:**
  1. Vía la API, delega la fase "Cálculo y Diseño (CD)" al usuario `ANGEL SALINAS`.
- **Resultado Esperado:**
  1. La tabla maestra de la cotización actualiza un campo JSONB o array de estados marcando la fase CD como `PENDIENTE` (lo que el frontend dibuja rojo 🔴).
  2. El backend genera una sub-tarea o registro relacionado, asignado a `ANGEL SALINAS`, agregándole automáticamente la marca `[Calculo y Diseño]` en su descripción.

### Escenario 5.2: Sync Inverso (Reverse Sync)
- **Precondición:** (Sigue de arriba). Angel tiene la sub-tarea activa.
- **Pasos:**
  1. Angel envía un PATCH marcando su sub-tarea al 100% y adjunta una URL del Storage (bucket) para el campo de cotización.
- **Resultado Esperado:**
  1. Su sub-tarea queda archivada/completada.
  2. Un Trigger en Supabase (o un background task en Python) detecta la finalización, localiza el registro padre `AV-5050`, inyecta la URL del archivo en la cotización maestra, y actualiza el estado de la fase CD a `COMPLETADO` (lo que el frontend dibuja verde 🟢).

### Escenario 5.3: Prevención de Cierre Prematuro (Master Lock)
- **Precondición:** Durante el *Reverse Sync* de la tarea `AV-5050`.
- **Pasos:**
  1. Angel envía el payload con estado `DONE` y avance `100`.
- **Resultado Esperado:** El backend de Python **bloquea y desecha** del payload los campos genéricos de estatus global. Aplica el completado solo a la "fase" asignada, impidiendo que el 100% de la sub-tarea sobreescriba el porcentaje total de la oportunidad de ventas principal en la DB.

## 6. Pruebas del Agente KPI, IA y Notificaciones
**Objetivo:** Confirmar el cierre del ciclo de reportes y workers programados.

### Escenario 6.1: Contabilidad de Métricas en Base de Datos
- **Precondición:** Cotización activa.
- **Pasos:**
  1. Antonia envía PATCH con estatus terminal `PERDIDA X PRECIO`.
  2. Consultar el endpoint de análisis de métricas.
- **Resultado Esperado:** Las vistas materializadas o agregaciones (SQL) en Supabase contabilizan el registro inmediatamente bajo el bucket de "Perdidas", actualizando en tiempo real la Tasa de Cierre global.

### Escenario 6.2: Gemini Integration Context (Worker en Python)
- **Precondición:** Se ejecuta la tarea programada (cronjob/Celery) de reporte mensual.
- **Pasos:**
  1. El worker invoca la función de reportes.
- **Resultado Esperado:** El script en Python ejecuta la consulta agregada (agrupando SLAs, ganadas/perdidas), envía el payload JSON a la API de Gemini, y guarda el resumen (180 palabras y recomendación) en la base de datos o lo despacha directo por correo.

### Escenario 6.3: Webhooks y Formato UTC
- **Precondición:** Creación de tarea nueva asignada a un usuario.
- **Pasos:**
  1. Revisar los logs del worker asíncrono o la tabla de auditoría en Supabase.
- **Resultado Esperado:**
  - El sistema detecta el cambio e invoca el Webhook hacia Make.com/Outlook.
  - La fecha del evento (`fechaInicio`) se serializa estrictamente en formato ISO 8601 (`YYYY-MM-DDTHH:mm:ss.sssZ`), asegurando que las zonas horarias no se corrompan entre la base de datos PostgreSQL (UTC) y el cliente final de correo.

## 13. Pruebas de Cronjobs (Contador Diario de SLAs)
**Objetivo:** Tareas en background programadas.

### Escenario 13.1: Actualización de Días Transcurridos
- **Pasos:** Ejecutar manualmente o esperar la ejecución nocturna del Job de Python (ej. Celery/APScheduler o pg_cron).
- **Resultado Esperado:**
  1. El script recalcula la diferencia de días (`CURRENT_DATE - fecha_inicio`).
  2. Actualiza la columna `dias_transcurridos` en la tabla de tareas.
  3. Esto alimenta en cascada las vistas del frontend para que rendericen los semáforos correctos al empezar la jornada.
